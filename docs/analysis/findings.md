# 解析記録

この記録は非公式で無保証です。法的な助言ではなく、記載の行為が適法であることや使用許諾に違反しないことを保証しません。詳細は [README の免責事項](../../README.md#免責事項) を参照してください。

各項目の状態は次のいずれかです。

- **観測済み**: 手元の実機で確認し、再現手順がある
- **仮説**: 外部の資料にしか根拠がない
- **不一致**: 観測と資料が食い違う

## 接続情報

再現コマンド（どちらもキーボードにレポートを送信しません）:

```sh
cargo run -p hhkb -- list
hidutil list --matching '{"VendorID":0x4fe}'
```

| 項目 | 内容 | 状態 | 根拠 |
|---|---|---|---|
| USB ID | `04fe:0021` | 観測済み | `hhkb list`、`hidutil list` |
| USB の製品名 | `HHKB-Hybrid` | 観測済み | `hhkb list`、`hidutil list` |
| USB のバージョン | `0x0001` | 観測済み | `hhkb list` |
| キーボード用インターフェース | Usage Page `0x0001` / Usage `0x0006` | 観測済み | `hhkb list`、`hidutil list` |
| 複合インターフェース | Usage `0x000c/0x0001` と `0x0001/0x0006` を持つ | 観測済み | `hhkb list` |
| ベンダー定義インターフェース | Usage Page `0xff00` / Usage `0x0001` | 観測済み | `hhkb list`、`hidutil list` |
| Bluetooth 側の表示 | 同じ ID で製品名 `HHKB-Hybrid_1` | 観測済み | `hidutil list` |
| Bluetooth 側の除外 | `hhkb list` は USB のインターフェースだけを表示する | 観測済み | Bluetooth 接続中の `hhkb list` |
| 更新用インターフェース | `0xff00` を更新に使う | 仮説 | [l3tnun/hhkb_hybrid の device-state.md](https://github.com/l3tnun/hhkb_hybrid/blob/main/docs/device-state.md) |
| 純正 FW と更新モードの区別 | USB の表示では区別できず、キー入力の可否で見分ける | 仮説 | [l3tnun/hhkb_hybrid の device-state.md](https://github.com/l3tnun/hhkb_hybrid/blob/main/docs/device-state.md) |

macOS の `hidapi` が返すパス `DevSrvsID:<値>` の値は、`hidutil list` の RegistryID を 10 進数にしたものと一致します。この値は再接続で変わる可能性があるので、機器の識別には使いません。

| 公式ツールへの読み込み | `scripts/run-official-tool.sh --expect-no-device probe` で読み込みと記録の開始を確認（キーボードなし） | 観測済み |

## 記録開始前の操作

通信の記録を始める前に、ユーザーが公式ツールでキーマップの書き込みを 3 回行いました。レポートの中身は記録していません。

## 公式ツールのログから分かった順序

公式ツールのログ（`~/Library/Application Support/hhkb-keymap-tool/`）で確認した順序です。ログには番号だけがあり、レポート内の位置と内容は未確認です。ログにはシリアル番号が含まれるので、内容は転記しません。

| 操作 | コマンドの順序 | 状態 |
|---|---|---|
| 起動時（操作なし） | `01 → 02 → 05 → 87×4 → 06 → 09 → 01` | 観測済み |
| キーマップの書き込み | `01 → 02 → 05 → 06 → 86×4 → 08 → 04 → 07 → 01` | 観測済み |

## レポートの形式

`probe` モードで、最初のレポートを実機に送らずに記録しました。

```sh
./scripts/run-official-tool.sh probe
```

| 項目 | 内容 | 状態 |
|---|---|---|
| 送信先 | Usage Page `0xff00`、Output レポート、レポート ID `0` | 観測済み |
| 長さ | 64 バイト | 観測済み |
| 最初のレポート | `aa aa 01 00 01` に続けてすべて `00` | 観測済み |
| 送信の先頭 2 バイト | すべて `aa aa` | 観測済み |
| コマンドの位置 | 3 バイト目（オフセット 2） | 観測済み |

### 読み出しの記録

`read` モードで、起動から正常終了までを記録しました。公式ツールの署名は前後とも検証に成功し、キーボードのキー入力とは別に、`0xff00` の通信だけを全バイト記録しています。

```sh
./scripts/run-official-tool.sh read 2
```

送信（64 バイト、残りは `00`）:

| コマンド | 公式ツールのログの関数名 | 送信の先頭 | 応答数 | 応答の長さ |
|---|---|---|---|---|
| `01` | `NotifyApplicationState` | `aa aa 01 00 01 00`（開始）、`aa aa 01 00 01 01`（終了） | 1 | 0 |
| `02` | `GetKeyboardInformation` | `aa aa 02` | 1 | 57 |
| `05` | `GetDipswInformation` | `aa aa 05` | 1 | 12 |
| `87` | `GetKeymap(mode:fnKey:isShortcut:)` | `aa aa 87 00 02 <mode> <fn>` | 3 | 58、58、12 |
| `06` | `GetKeyboardMode` | `aa aa 06` | 1 | 1 |
| `09` | `GetSleepSetting` | `aa aa 09` | 1 | 1 |

応答（64 バイト）の形式:

| 位置 | 内容 | 状態 |
|---|---|---|
| 0〜1 | `55 55` | 観測済み |
| 2 | 送信と同じコマンド | 観測済み |
| 3 | 今回はすべて `00`。結果コードと推定 | 仮説 |
| 4 | 分割なしは `00`、3 分割は `41`、`82`、`c3`。分割の番号と推定 | 仮説 |
| 5 | データ長 | 観測済み（残りがすべて `00` であることと、合計 128 バイトで確認） |
| 6〜 | データ | 観測済み |

`.hks` との照合（値は記録しません）:

| 項目 | 結果 | 状態 |
|---|---|---|
| `87` の `mode=01 fn=1` | `WithFn` と 128 バイトすべて一致 | 観測済み |
| `87` の `mode=01 fn=0` | `Normal` と 1 バイト（位置 50）だけ異なる。原因は未確認 | 不一致 |
| `87` の `mode=11` | `fn` の値によらず同じデータで、`.hks` とは異なる。意味は未確認 | 観測済み |
| `05` | 先頭 6 バイトが `DipSwitch` と一致 | 観測済み |
| `09` | データ長は 1 で、`SleepSetting` の値と直接は一致しない。符号化は未確認 | 不一致 |

## HFB の構造

純正の更新ファイル `HHKB800_FW_A048.hfb` を読み取り専用で調べました。実行コードの逆アセンブルはしていません。ファイルは公開せず、値の中身も転記しません。

再現コマンド（実機とは通信せず、入力ファイルも変更しません）:

```sh
cargo run -p hhkb -- inspect local/HHKB800_FW_A048.hfb
shasum -a 256 local/HHKB800_FW_A048.hfb
```

解析した純正 HFB の SHA-256 は `635b995eb5a15aa50c2cedc60da7d8998fcca8285a09d41d984c07fffcaf9d43` です。

### 領域

全体は `0x45030` バイトです。

| 範囲 | 内容 | 状態 |
|---|---|---|
| `0x00000`〜`0x00002` | 全体の CRC（リトルエンディアン） | 観測済み |
| `0x00002`〜`0x00004` | 領域 A の CRC（リトルエンディアン） | 観測済み |
| `0x00004`〜`0x10004` | 領域 A（`0x10000` バイト） | 観測済み |
| `0x10004`〜`0x10010` | 詰め物。すべて `ff` | 観測済み |
| `0x10010`〜`0x10020` | 領域 B の MD5 | 観測済み |
| `0x10020`〜`0x45020` | 領域 B（`0x35000` バイト） | 観測済み |
| `0x45020`〜`0x45026` | ASCII の識別子 `AHUX01` | 観測済み |
| `0x45026`〜`0x45028` | 識別子の終端 `0a 00` | 観測済み |
| `0x45028`〜`0x4502a` | アプリ領域の版 | 観測済み |
| `0x4502a`〜`0x45030` | 詰め物。すべて `ff` | 観測済み |

領域の用途は確定していません。

| 項目 | 内容 | 状態 |
|---|---|---|
| 領域 A の用途 | `0x0801xxxx` を指すベクタテーブルに見える部分が先頭にある。STM32 のアプリ領域と推定 | 仮説 |
| 領域 B の用途 | `0x10020` と `0x35020` にベクタテーブルに見える部分がある。nRF 側のイメージと推定 | 仮説 |

### 整合性

| 検査 | 対象範囲 | 計算方法 | 純正 HFB | 状態 |
|---|---|---|---|---|
| 全体 CRC | `0x00002`〜`0x45030` | CRC-16（多項式 `0x1021`、入出力反転、初期値 `0xffff`、最終 XOR なし） | 一致 | 観測済み |
| 領域 A CRC | `0x00004`〜`0x10004` | 同上 | 一致 | 観測済み |
| 領域 B MD5 | `0x10020`〜`0x45020` | MD5 | 一致 | 観測済み |

計算方法は、多項式、反転、初期値、対象範囲の組み合わせを探索して特定しました。根拠と限界は次のとおりです。

- 2 つの値が同じ計算方法で、それぞれフィールドの直後から領域の境界までの範囲と一致しました
- 比較した純正 HFB は 1 つだけです。16 ビットの値なので、他の版での確認が取れれば根拠が強くなります
- 実機や公式ツールが更新時にこれらの値を検査するかは未観測です

1 バイトの改変で次の結果になることを、純正 HFB のコピーで確認しました。どちらも終了コードは 1 です。

| 改変した位置 | 全体 CRC | 領域 A CRC | 領域 B MD5 |
|---|---|---|---|
| `0x00100`（領域 A） | 不一致 | 不一致 | 一致 |
| `0x20000`（領域 B） | 不一致 | 一致 | 不一致 |

### 機種と版

| 項目 | 内容 | 状態 |
|---|---|---|
| 版の符号化 | 2 バイトを 1 桁ずつ読む。`04 08` が `A0.48` に対応する | 観測済み（`02` の応答と公式ツールのログの版で確認） |
| `AHUX01` と機種の対応 | `PD-KB800BNS` 向けに入手した純正 HFB で観測した。`02` の応答と公式ツールのログには現れず、他の機種の値も未確認 | 仮説 |

CLI は `AHUX01` だけを既知の識別子として扱います。それ以外の識別子や、数字として読めない版は「未確定」と表示し、終了コード 1 を返します。

### 読み取り専用と入力の検査

| 項目 | 結果 | 状態 |
|---|---|---|
| 入力ファイルの SHA-256 | 純正 HFB の解析前後で変わらない。合成データのテストでも確認した | 観測済み |
| 短すぎるファイル | ヘッダより短い場合は理由を表示し、終了コード 1 を返す | 観測済み |
| サイズが異なるファイル | 推測で解釈せず、理由を表示して終了コード 1 を返す | 観測済み |

自動テストは `cargo test -p hhkb --test hfb` で実行できます。テストには合成データを使い、純正 HFB には依存しません。

## 状態確認 CLI

承認済みのレポートはまだありません。`hhkb status` はデバイスを開かず、何も送信せずに一覧の情報だけを表示します。

```sh
cargo run -p hhkb -- status
cargo test -p hhkb --lib status
```

| 項目 | 確認方法 | 結果 | 状態 |
|---|---|---|---|
| 承認済みのレポートがないときの動作 | 実機が接続された状態の実行とモックのテスト | デバイスを開かず、何も送信しない | 観測済み |
| 公式ツールの実行中の拒否 | 同じプロセス名のダミーを動かして実行。公式ツールは起動していない | 終了コード 1 で、デバイスを開かない | 観測済み |
| 公式ツールの確認に失敗したときの動作 | モックのテスト | 実行中と同じく中止する | 観測済み |
| 開くインターフェース | モックのテスト | `0xff00` だけを開く。他の用途と同じインターフェースなら開かない | 観測済み |
| タイムアウトと再送 | モックのテストの送信回数 | 送信は 1 回だけで、後続のレポートも送らない | 観測済み |
| バイト列を受け取る公開 API と CLI オプション | `pub` の一覧と `hhkb status --help` のレビュー | 存在しない | 観測済み |

次の 2 点はまだ実機で確かめていません。承認済みのレポートがないと通らない経路なので、タスク 5.4 で確認します。

- 非排他で開くこと。`set_open_exclusive(false)` の指定をコードで確認しただけで、モックでは確認できません
- hidapi 経由の実際のオープンと送受信
