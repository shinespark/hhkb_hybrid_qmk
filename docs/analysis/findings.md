# 解析記録

この記録は非公式で無保証です。詳細は [README の免責事項](../../README.md#免責事項) を参照してください。

各項目の状態は次のいずれかです。

- **観測済み**: 手元の実機で確認し、再現手順がある
- **仮説**: 外部の資料にしか根拠がない
- **不一致**: 観測と資料が食い違う

## 接続情報

再現コマンド（どちらもキーボードにレポートを送信しません）:

```sh
cargo run -p hhkb -- list
hidutil list --matching '{"VendorID":0x4fe}'
```

| 項目 | 内容 | 状態 | 根拠 |
|---|---|---|---|
| USB ID | `04fe:0021` | 観測済み | `hhkb list`、`hidutil list` |
| USB の製品名 | `HHKB-Hybrid` | 観測済み | `hhkb list`、`hidutil list` |
| USB のバージョン | `0x0001` | 観測済み | `hhkb list` |
| キーボード用インターフェース | Usage Page `0x0001` / Usage `0x0006` | 観測済み | `hhkb list`、`hidutil list` |
| 複合インターフェース | Usage `0x000c/0x0001` と `0x0001/0x0006` を持つ | 観測済み | `hhkb list` |
| ベンダー定義インターフェース | Usage Page `0xff00` / Usage `0x0001` | 観測済み | `hhkb list`、`hidutil list` |
| Bluetooth 側の表示 | 同じ ID で製品名 `HHKB-Hybrid_1` | 観測済み | `hidutil list` |
| Bluetooth 側の除外 | `hhkb list` は USB のインターフェースだけを表示する | 観測済み | Bluetooth 接続中の `hhkb list` |

### キーマップ書き込みの記録

`keymap-write` モードで、公式ツールから 1 キーを変更して元に戻す書き込みを記録しました。キーマップの値は記録しません。

```sh
./scripts/run-official-tool.sh keymap-write 2
./scripts/run-official-tool.sh read 2
```

操作は次の 2 回の書き込みです。

1. `Normal` の 0 キーを 9 に変更した
2. 同じキーを手作業で 0 に戻した。`.hks` は読み込んでいない

送信（64 バイト、残りは `00`）:

| コマンド | 公式ツールのログの関数名 | 送信の先頭 | 応答 |
|---|---|---|---|
| `86` | `SetKeymap(mode:fnKey:keymapData:isShortcut:)` | `aa aa 86 <分割> <長さ>` に続けてデータ | 分割ごとに 1 レポート、データ長 0 |
| `08` | `ResetSleepSetting(sleepSetting:)` | `aa aa 08 00 01 <値>` | 1 レポート、データ長 0 |
| `04` | `ConfirmKeymap` | `aa aa 04` | 1 レポート、データ長 0 |
| `07` | `ResetDIPSW(keyboardMode:)` | `aa aa 07 00 01 <値>` | 1 レポート、データ長 0 |

応答の 4 バイト目はすべて `00` でした。

`86` の形式:

| 項目 | 内容 | 状態 |
|---|---|---|
| 分割 | 1 回の書き込みを 3 レポートに分け、オフセット 3 は `41`、`82`、`c3`。上位 2 ビットが番号、下位 6 ビットが総数と推定 | 仮説 |
| 長さ | オフセット 4 に各レポートのデータ長。`3b`、`3b`、`0c` で合計 130 バイト | 観測済み |
| データ | 先頭の 2 バイトが `mode` と `fn`、続く 128 バイトがキーマップ | 観測済み |
| 順序 | `mode=01 fn=0`、`mode=01 fn=1`、`mode=11 fn=0`、`mode=11 fn=1` | 観測済み |
| 間隔 | レポートの送信間隔は約 13 ミリ秒。各応答を受けてから次を送っている | 観測済み |

`08` の値は `09` の応答と、`07` の値は `06` の応答と同じでした。1 組の観測なので、読み出した値をそのまま書き戻しているかは確定していません。

変更箇所:

| 比較 | 結果 | 状態 |
|---|---|---|
| 1 回目と 2 回目の書き込み | 異なるのは `mode=01 fn=0` の位置 50 だけ | 観測済み |
| 1 回目の書き込みと、基準の読み出し | `mode=01 fn=0` の位置 50 だけ異なる | 観測済み |
| 2 回目の書き込みと、基準の読み出し | 4 つとも全バイト一致 | 観測済み |
| 位置とキーの対応 | 位置 50 は 0 キー | 観測済み |
| 実際の入力 | 1 回目の後は 0 キーで 9 が、2 回目の後は 0 が入力された（ユーザーが確認） | 観測済み |
| `mode=11` | `87` で読み出した内容をそのまま書き込んでいる。意味は未確認 | 観測済み |

復元の確認:

| 項目 | 結果 | 状態 |
|---|---|---|
| 書き込み前と書き込み後の読み出し | 送信 10 件と応答 18 件の全バイトが一致 | 観測済み |
| 公式ツールの署名 | 2 回の記録の前後とも検証に成功 | 観測済み |
| ロガーの中止と送信エラー | なし | 観測済み |

次の点は確かめていません。

- `04` の役割。関数名からキーマップの確定と推定していますが、`04` なしの動作は試していません
- 電源を切った後も書き込みが保持されること
- 読み出しに現れないファームウェア内部の状態が変わっていないこと

### `.hks` を復元の基準にしない

`local/` の `.hks` は、`Normal` の位置 50 が 9 で、0 が含まれません。読み込むと 0 キーで 9 が入力される可能性があるので、復元には使いません。

| 項目 | 内容 | 状態 |
|---|---|---|
| 差の位置 | `Normal` の位置 50 だけ。実機の読み出しは 0 | 観測済み |
| 順序 | `.hks` の保存の 1 秒後に書き込みがあり、以降はこの検証まで書き込みがない | 観測済み |
| 原因 | 編集途中の状態を保存した後に書き込んだと推定。読み込みは試していない | 仮説 |

復元の基準には、読み出しの記録を使います。`.hks` の保存が必要なときは、書き込みの後に保存し、読み出しの記録と比較します。

上の `.hks` は、次の保存で同じファイル名に上書きされ、現在は残っていません。

### `.hks` の保存と同時に書き込みが送られる

`read` モードで `.hks` を保存すると、公式ツールは保存に続いて `01`、`02`、`05`、`06` を送り、次の `86` がロガーに止められて、公式ツールは終了コード 134 で中止しました。

| 項目 | 内容 | 状態 |
|---|---|---|
| 順序 | 公式ツールのログのファイル書き込みと `86` の送信の試みが同じ秒にある | 観測済み |
| 実機への `86` | ログの種別は `out-blocked` で、送信されていない | 観測済み |
| 終了の通知 | 2 回目の `01 00 01 00` の後に、`01 00 01 01` が送られないまま中止した。実機への影響は未確認 | 観測済み |
| 保存の結果 | 中止の前にファイルは保存され、`Normal` と `WithFn` は読み出しの mode `01` の 2 つと全バイト一致した | 観測済み |
| 原因 | 公式ツールの保存の操作に実機への書き込みが含まれる。前回の保存の 1 秒後の書き込みとあわせて 2 回の観測で、操作の内訳は確認していない | 仮説 |

`.hks` は `Normal` と `WithFn` だけを持ち、mode `11` の 2 つは含みません。

### `.hks` からの復元

`.hks` の読み込みで実機と同じ内容になるときは、`Write to HHKB` を押せませんでした。そこで、1 キーを変更して書き込んだ後に `.hks` を読み込み、書き込んで戻しました。

| 段階 | 記録の内容 | 状態 |
|---|---|---|
| 変更の書き込み | `Normal` の位置 50 だけが基準と異なり、応答はすべて正常 | 観測済み |
| `.hks` の書き込み | 4 つのキーマップ、`08`、`07` の送信値がすべて基準と同じで、応答はすべて正常 | 観測済み |
| 復元後の読み出し | 基準の記録と全 28 フレームが一致 | 観測済み |
| 復元後の入力 | 0 キーで `0` が入力された | 観測済み |

mode `11` は今回の変更の対象ではなく、基準と同じ値のままです。mode `11` が変わった状態から `.hks` で戻るかは確かめていません。公式ツールが送った mode `11` の値が、`.hks` にない値をどこから得たかも未確認で、読み出した値を送っていると推定します。電源を切った後の保持も未確認です。

## HFB の構造

公式の更新ファイル `HHKB800_FW_A048.hfb` を読み取り専用で調べました。実行コードの逆アセンブルはしていません。ファイルは公開せず、値の中身も転記しません。

再現コマンド（実機とは通信せず、入力ファイルも変更しません）:

```sh
cargo run -p hhkb -- inspect local/HHKB800_FW_A048.hfb
shasum -a 256 local/HHKB800_FW_A048.hfb
```

解析した公式 HFB の SHA-256 は `635b995eb5a15aa50c2cedc60da7d8998fcca8285a09d41d984c07fffcaf9d43` です。

### 領域

全体は `0x45030` バイトです。

| 範囲 | 内容 | 状態 |
|---|---|---|
| `0x00000`〜`0x00002` | 全体の CRC（リトルエンディアン） | 観測済み |
| `0x00002`〜`0x00004` | 領域 A の CRC（リトルエンディアン） | 観測済み |
| `0x00004`〜`0x10004` | 領域 A（`0x10000` バイト） | 観測済み |
| `0x10004`〜`0x10010` | 詰め物。すべて `ff` | 観測済み |
| `0x10010`〜`0x10020` | 領域 B の MD5 | 観測済み |
| `0x10020`〜`0x45020` | 領域 B（`0x35000` バイト） | 観測済み |
| `0x45020`〜`0x45026` | ASCII の識別子 `AHUX01` | 観測済み |
| `0x45026`〜`0x45028` | 識別子の終端 `0a 00` | 観測済み |
| `0x45028`〜`0x4502a` | アプリ領域の版 | 観測済み |
| `0x4502a`〜`0x45030` | 詰め物。すべて `ff` | 観測済み |

領域の用途は確定していません。

| 項目 | 内容 | 状態 |
|---|---|---|
| 領域 A の用途 | `0x0801xxxx` を指すベクタテーブルに見える部分が先頭にある。STM32 のアプリ領域と推定 | 仮説 |
| 領域 B の用途 | `0x10020` と `0x35020` にベクタテーブルに見える部分がある。nRF 側のイメージと推定 | 仮説 |

### 整合性

| 検査 | 対象範囲 | 計算方法 | 公式 HFB | 状態 |
|---|---|---|---|---|
| 全体 CRC | `0x00002`〜`0x45030` | CRC-16（多項式 `0x1021`、入出力反転、初期値 `0xffff`、最終 XOR なし） | 一致 | 観測済み |
| 領域 A CRC | `0x00004`〜`0x10004` | 同上 | 一致 | 観測済み |
| 領域 B MD5 | `0x10020`〜`0x45020` | MD5 | 一致 | 観測済み |

計算方法は、多項式、反転、初期値、対象範囲の組み合わせを探索して特定しました。根拠と限界は次のとおりです。

- 2 つの値が同じ計算方法で、それぞれフィールドの直後から領域の境界までの範囲と一致しました
- 比較した公式 HFB は 1 つだけです。16 ビットの値なので、他の版での確認が取れれば根拠が強くなります
- 実機や公式ツールが更新時にこれらの値を検査するかは未観測です

1 バイトの改変で次の結果になることを、公式 HFB のコピーで確認しました。どちらも終了コードは 1 です。

| 改変した位置 | 全体 CRC | 領域 A CRC | 領域 B MD5 |
|---|---|---|---|
| `0x00100`（領域 A） | 不一致 | 不一致 | 一致 |
| `0x20000`（領域 B） | 不一致 | 一致 | 不一致 |

### 機種と版

| 項目 | 内容 | 状態 |
|---|---|---|
| 版の符号化 | 2 バイトを 1 桁ずつ読む。`04 08` が `A0.48` に対応する | 観測済み（`02` の応答と公式ツールのログの版で確認） |
| `AHUX01` と機種の対応 | 公式ツールは HFB の読み込み時に、この値を `appliableKeyboard` としてログに出す。`02` の応答には現れず、他の機種の値も未確認 | 仮説 |

CLI は `AHUX01` だけを既知の識別子として扱います。それ以外の識別子や、数字として読めない版は「未確定」と表示し、終了コード 1 を返します。

### 読み取り専用と入力の検査

| 接続方法 | 仮想マシンではない Linux に USB で接続 |
| 認識 | `HHKB-Hybrid` が 1 台 |
| 更新用インターフェース | `input2`、ディスクリプタの先頭 `06 00 ff`、`FLASH TARGET` と表示 |
| 公式 HFB | SHA-256 と CRC が一致、4,960 パケット、`stock (no QMK)` と判定 |
| 権限 | udev ルールの追加と USB の抜き差しの後、`--list` の権限の警告が消えた |

`--list` はシリアル番号を表示します。出力を共有するときは隠します。`--trace-log` のログには HFB の内容が残るので、公開しません。

### 準備

- `tools/flash.py` は `/dev/hidraw*` を読み書きするので、権限が必要です。`/etc/udev/rules.d/70-hhkb-hybrid.rules` に次のルールを置き、`sudo udevadm control --reload-rules` の後に USB を抜き差しします。`sudo chmod` は、再列挙で `hidraw` の番号が変わるので使えません

  ```
  SUBSYSTEM=="hidraw", ATTRS{idVendor}=="04fe", ATTRS{idProduct}=="0021", TAG+="uaccess"
  ```

- 更新モードでは HHKB から入力できない可能性があるので、Linux を操作できる別のキーボードを用意します
- HHKB とペアリングした Mac と Linux の Bluetooth を切ります。資料には、Bluetooth 接続時にパケット 1149 の次で転送が止まる例があります
- ハブを使わず直結し、Linux の電源とスリープの設定を確認します

### 手順

参考実装のディレクトリで実行します。

1. HFB と状態を確認します

   ```sh
   echo "635b995eb5a15aa50c2cedc60da7d8998fcca8285a09d41d984c07fffcaf9d43  ../HHKB800_FW_A048.hfb" | sha256sum -c -
   python3 tools/flash.py --dry-run ../HHKB800_FW_A048.hfb
   python3 tools/flash.py --list | sed -E 's/serial=[^ ]*/serial=<masked>/'
   ```

2. `FLASH TARGET` の `/dev/hidrawN` を確かめ、HHKB からキー入力できるかで状態を判断します。USB の表示では、公式ファームウェアと更新モードを区別できません

   | 状態 | 判断 | 次の操作 |
   |---|---|---|
   | キー入力できる | 公式ファームウェアで動作している | 復旧は不要。再度書き込むかは判断する |
   | キー入力できない | 更新モードの可能性がある | 手順 3 |
   | `FLASH TARGET` がない | 認識に失敗している可能性がある | USB を抜き差しして手順 1 に戻る |

3. 承認を得てから、`--resume` で書き込みます。`--allow-crc-mismatch` は使いません

   ```sh
   python3 tools/flash.py --resume --device /dev/hidrawN --trace-log <公開しない場所>/flash-trace.jsonl ../HHKB800_FW_A048.hfb
   ```

4. `done` の表示の後、USB の表示とキー入力を確認します。失敗したら、キー入力の可否を確かめて手順 1 に戻り、繰り返す前に判断します

`--resume` で失敗して HHKB からキー入力できる場合、更新モードではありません。この場合に `--resume` を繰り返しません。転送の途中で失敗した後の再開は資料でも確定していません。Linux でも戻らないときの最終手段は分解で、その判断は利用者に委ねます。

## QMK の書き込みと公式ファームウェアへの復帰

`hhkb flash` で、公式ファームウェアから `default` を書き込み、macOS だけで公式ファームウェアへ戻しました。手元の 1 台で 1 回ずつ実行した結果で、他の個体での動作や、途中で止まった場合の動作は確認していません。

### `via` の書き込みと公式ファームウェアへの復帰

公式ファームウェアから `via` を書き込み、VIA で確認した後に公式ファームウェアへ戻しました。**戻した後、公式ファームウェアのキーマップが基準から変わったので、`.hks` で戻しました。** `via` から戻すときは、キーマップの復元が必要になると考えておきます。

| 項目 | 結果 | 状態 |

| 書き込み | 転送の応答の 4 バイト目はすべて `00`。USB の表示は `default` と同じ | 観測済み |
