# Design

## Context

目的は proposal.md を参照。開発環境は Apple Silicon の macOS で、SIP は有効である。Docker と VM は入っていない。

実機と公式ツールについて、手元で観測済みの内容は次のとおり。

- USB では `04fe:0021`、製品名 `HHKB-Hybrid`、バージョン `0x0001` として見える
- USB の HID インターフェースは Usage Page `0x01`、`0x0C`、`0xFF00` の 3 つで、`0xFF00` の入力レポートは最大 64 バイト
- Bluetooth 側にも同じ ID のデバイスが `HHKB-Hybrid_1` として見える
- 公式ツールは arm64 を含むユニバーサルバイナリで、`IOHIDDeviceSetReport` と入力レポートのコールバックを使う
- 公式ツールには `allow-dyld-environment-variables` と `disable-library-validation` の entitlement があり、App Sandbox は使っていない
- 公式ツールのログには、操作なしの起動時に `01 → 02 → 05 → 87×4 → 06 → 09 → 01`、書き込み時に `01 → 02 → 05 → 06 → 86×4 → 08 → 04 → 07 → 01` の順で記録がある

ログにはコマンド番号だけがあり、レポート内の位置と内容は未確認である。`01` は状態を変える可能性があるため、読み取りとして扱わない。

## Goals / Non-Goals

**Goals:**

- 次の段階の判断に必要な事実を、macOS 上の観測で集める
- 自作ツールからは、記録と完全に一致する読み取りレポートだけを送る

**Non-Goals:**

- 汎用の HID コマンド送信機能。後続の書き込みは別のモジュールとして設計する
- macOS 以外への対応。ただし HFB の解析は OS に依存させない

## Decisions

### 通信の観測は dyld の関数差し替えで行う

Rust 製の cdylib を `DYLD_INSERT_LIBRARIES` で読み込ませ、`__DATA,__interpose` で `IOHIDDeviceSetReport`、`IOHIDDeviceRegisterInputReportCallback`、`IOHIDDeviceOpen`、`IOHIDDeviceClose` を差し替える。公式ツールの entitlement から動作する見込みだが、自作のテスト実行ファイルで差し替えを確かめてから適用する。

- 代替案: Wireshark の USB キャプチャ。SIP の変更が必要になる可能性があるので、差し替えが動かないときにユーザーへ相談する
- 代替案: ハードウェアの USB アナライザ。機材が必要なので、上記が使えないときの候補にする
- 代替案: VM と USB パススルーで Windows 版を観測する。macOS 版の通信そのものを見られないので採用しない
- 代替案: 逆アセンブル。今回の解析範囲に含めない

実装の方針:

- 入力コールバックは登録ごとに元の関数とコンテキストを保持してトランポリンで包む。解除の NULL はそのまま渡す。遅延呼び出しに備えて保持領域は解放しない
- ロックを持ったまま元の関数を呼ばない。送信前に内容を記録し、戻り値は送信後に記録する
- 1 レコードを `O_APPEND` で 1 回の `write(2)` にする
- パニックを `extern "C"` の外に出さない

起動はスクリプトから実行ファイルを直接起動する。`open` や SIP 保護された `/bin/sh` を経由すると `DYLD_*` が届かない可能性がある。arm64 で起動し、Rosetta を使わない。

### 安全弁はモードごとの許可リストにする

送信はモードごとの許可リストと照合し、一致しなければ送信せずに記録して中止する。送信成功の偽装は、公式ツールを想定外の状態に進めるので行わない。

| モード | 許可するもの | 用途 |
|---|---|---|
| `probe` | なし | 最初のレポートを送らずに記録し、コマンドの位置を確認する |
| `read` | `01`、`02`、`05`、`06`、`87`、`09` | 起動と読み出しの記録 |
| `keymap-write` | `read` に `86`、`08`、`04`、`07` を追加 | キーマップ書き込みの記録 |
| `firmware-update` | `0xFF00` への送信すべて | 純正ファームウェア再書き込みの記録 |

`probe` では何も実機に届かないので、最初のレポートの形式を安全に確認できる。コマンドの位置はこの結果で確定し、ユーザーに提示してから `read` を使う。`firmware-update` は段階の承認を得たときだけ指定する。

### 送信は固定レポートの列挙型に閉じる

送信はコード内の列挙型を通してのみ行い、各項目はレポート全体のバイト列を持つ。送信のトレイトは非公開にする。最初の候補は `0x02` の 1 つだけで、`01` が必須と分かった場合の扱いは 5.2 でユーザーが判断する。

- 代替案: 拒否リスト。未知のコマンドを送ってしまう可能性が残るため採用しない

### 対象は USB かつ `0xFF00` で選ぶ

Bluetooth 側も同じ VID/PID で見えるため、VID/PID だけでは絞り込まない。1 台が複数のインターフェースとして見えるので、`0xFF00` のインターフェースの数を台数とする。

### hidapi を使い、非排他で開く

macOS の IOKit を直接呼ばず、`hidapi` クレートを使う。C 実装の既定は排他オープンなので、`set_open_exclusive(false)` を指定してから開く。`hid_write` は先頭バイトをレポート ID として扱うので、送信形式はロガーの記録と照合する。

### クレートを 2 つに分ける

- `hhkb`: HFB 解析、HID 層、許可リスト、CLI
- `hid-logger`: dyld で読み込む cdylib

ロガーは公式ツールのプロセス内で動くため、依存を最小限にして分離する。

### 公式ツールのログは補助情報として使う

コマンドの順序を確認する補助に使う。シリアル番号が平文で含まれるので、内容をリポジトリに転記しない。

### 自前の観測を先に行い、参考実装とは後で照合する

先に参考実装の解析記録を読むと、観測がその答えをなぞりやすい。そのため記録と構造の解析を終えてから照合する。更新コマンドについては、レビューの過程で参考実装の記述を読んでいるので、独立した発見として扱わない。

### 第三者由来物と個体情報は `local/` に置く

純正 HFB、生ログ、`.hks` は `.gitignore` 対象の `local/` に置く。自動テストには、構造を模した合成データを使う。

## Risks / Trade-offs

- [公式ツールは起動しただけで実機と通信する] → 起動確認は USB を抜き、キーボードの電源を切って行う。記録は起動から正常終了までとし、強制終了しない
- [安全弁の中止で `01` の後の状態に残る] → 中止後は USB を抜き差しし、キー入力を確認する。手順は 3.6 に含める
- [ファームウェア更新の途中で失敗する] → 別の承認を得てから行う。ケーブルと電源を確認し、失敗時の復旧手順を先に確認する
- [公式の更新で版が変わり、後続の前提が崩れる] → 再書き込みには現在と同じ版だけを使う。更新の通知には従わない
- [macOS だけでは復旧できない] → 復帰手段を確認するまで QMK を書き込まない
- [差し替えが EULA に抵触する可能性] → 法的な判断はできないため、実行前にユーザーの判断を得る。バイナリは変更しない
- [読み取りに見えるコマンドが状態を変える] → 許可するレポートを最小にし、前後の応答を比較する
- [打鍵内容やシリアル番号がログに残る] → 全バイト記録を `0xFF00` に限定し、権限を 0600 にする。`0xFF00` の応答に含まれる個体情報は転記しない
- [HFB 内の CRC 計算を自前で特定できない] → 特定できない場合は「仮説」と記録し、参考実装と照合する

## Migration Plan

観測の範囲では、自作ツールは実機を変更しない。公式ツールでの書き込みと再書き込みは実機を変更するので、キーマップは公式ツールで手作業で戻し、読み出しの記録と全バイトを比較して確認する。`local/` の `.hks` は実機と 1 キー異なるので、復元に使わない。公式ツールを通常どおり起動すれば、ロガーは読み込まれない。

## Open Questions

- 純正 FW と更新モードを、公式ツールが記録する `RunningFirmwareState` や応答で区別できるか。純正の再書き込みを記録すれば手がかりが増える。区別できない場合は仕様どおりキー入力の確認へ案内する
