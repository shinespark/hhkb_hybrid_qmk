# Proposal

## Why

macOS から純正を書き込めることは確かめたので、次は QMK を書き込むための HFB が要る。キーボード定義を自前で確かめるには分解か逆アセンブルが必要で、逆アセンブルはしないと決めている。そこで、まず実績のある参考実装の定義をコミット固定で参照し、ビルドと HFB の生成を手元で再現できるようにする。

## What Changes

- 参考実装 `l3tnun/hhkb_hybrid` をコミット固定の submodule で参照する。キーボード定義のファイルはこのリポジトリにコピーしない
- 固定した QMK 本体と Docker イメージで、`default` と `via` の 2 つの keymap をビルドする CLI を追加する
- ビルドした `.bin` の SHA-256 を、期待する値と照合する。期待する値は、参考実装の公開値でビルドの方法を確かめたうえで、固定したコミットの実測値にする
- 純正 HFB をテンプレートに、STM32 のアプリ領域だけを `.bin` に置き換えて CRC を計算し直す、Rust の HFB 生成 CLI を追加する
- 生成した HFB と `.bin` は `local/` に置き、公開も配布もしない
- `README.md` の注意事項と、参考実装の扱いの記述を更新する
- 範囲外:
  - 実機への書き込み。`hhkb flash` の許可リストは変更せず、生成した HFB は拒否されたままにする
  - キーボード定義の自作、キーマップの変更
  - Bluetooth、電源管理の動作の確認
  - 途中で止まった状態から戻せるかの実機での確認。次の change で、QMK の書き込みの前に行うかを判断する

## Capabilities

### New Capabilities

- `qmk-build`: 固定した入力から QMK をビルドし、成果物が期待する値と一致することを確かめる
- `hfb-generation`: 許可した純正 HFB と、許可した QMK の `.bin` から HFB を生成する

### Modified Capabilities

なし。`firmware-update` の許可リストの要件は変わらない。

## Impact

- コード: `crates/hhkb` に `qmk` サブコマンドとモジュールを追加する
- リポジトリ: submodule を 1 つ追加する。参照先の URL とコミットだけが入り、参考実装のファイルは入らない
- 環境: Mac に Docker Desktop を導入する。導入と実行は承認を得てから行う。参考実装の QMK 本体、ChibiOS などの取得に、ネットワークとディスク容量が要る
- 実機: 触れない
- 法的な扱い: 参考実装の定義には、公式ファームウェアの逆アセンブルで得た知見が反映されている。手元で使うことの判断はユーザーに委ねていて、この change は適法性を判断しない。生成した HFB には PFU 製の nRF イメージが含まれるので配布しない。`.bin` は GPL-2.0 の結合著作物で、これも配布しない
