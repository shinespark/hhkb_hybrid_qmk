# Proposal

## Why

QMK の書き込みと純正への復帰を macOS で行うには自作のツールが要るが、更新の手順は参考実装の資料にしか根拠がなく、macOS での動作は誰も記録していない。更新モードに入ると書き込みが終わるまでキー入力できない可能性があるので、QMK より先に、実機と同じ純正 `A0.48` の再書き込みで経路と復旧を確かめる。

## What Changes

- 復旧用の Linux 環境を用意し、参考実装のツールで実機を認識できることを確認する
- 現在の設定のバックアップと、公式ツールでの復元を確認する
- 承認を得て、Linux から参考実装のツールで純正を再書き込みし、更新の通信と設定の維持を観測する
- macOS 用の Rust 製の書き込み CLI を追加する。対象は SHA-256 で許可した純正 `A0.48` の HFB だけとする
- CLI の実行を、書き込みの計画、更新モードへの移行、本体の書き込みの 3 段階に分け、実機に触れる段階はそれぞれ承認を得てから行う
- macOS から純正を再書き込みし、更新モードの見え方、再列挙、応答、タイミング、設定の維持、復帰の成否を解析記録に残す
- 範囲外:
  - QMK のビルドと書き込み
  - 版を書き換えた HFB、別の版の書き込み
  - DFU による復旧の実施。分解が必要なので、手順の参照だけにとどめる
  - バイナリの逆アセンブル

### 全体の段階

検証の結果を受けて、段階を次の順に変更する。

1. 完了: 検証、読み取り専用ツール、公式ツールの通信の記録
2. この change: macOS からの純正の再書き込みと復旧の確認（Rust）
3. 次の change: QMK のビルドと HFB 生成（Rust）
4. その次の change: macOS からの QMK の書き込みと純正への復帰

## Capabilities

### New Capabilities

- `firmware-update`: 許可した純正 HFB だけを、段階と確認を経て実機に書き込み、失敗時に次の手順を案内する

### Modified Capabilities

- `device-status`: 固定のレポートだけを送信するという要件の対象を、状態確認に限定する。書き込みの要件は `firmware-update` で定める

## Impact

- コード: `crates/hhkb` に書き込みのモジュールと `flash` サブコマンドを追加する。`sha2` を通常の依存に移す
- 実機: 純正の再書き込みでキーボードの内部状態が変わる。設定が失われる可能性がある。失敗すると、Linux からの復旧や、最終手段として分解が必要になる可能性がある
- 保証: 純正の更新ファイルでも、非公式の手段で書き込むと保証に影響する可能性がある
- 外部: Linux 環境と、固定したコミットの参考実装のツールを復旧に使う。参考実装のツールはリポジトリに含めない
- ドキュメント: `README.md` の注意事項と `docs/analysis/findings.md` を更新する
