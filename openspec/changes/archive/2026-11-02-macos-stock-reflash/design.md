# Design

## Context

目的は proposal.md を参照。既存の `crates/hhkb` には、HFB の解析、USB の対象選択、`02` の固定レポートを送る状態確認がある。状態確認の送信処理は非公開で、モック HID のテストがある。

手元で観測済みの内容:

- 純正 FW の `0xFF00` は `hidapi` で開いて、64 バイトのレポートを送受信できる
- `02` の応答に、アプリ領域とブート領域の版が含まれる
- 公式ツールは同じ版の HFB を書き込まない

次の内容は参考実装の資料だけが根拠で、この change の観測で確かめる。

- `e0` で更新モードへ移り、`e1` にサイズと HFB の CRC を渡し、`e2` で HFB のオフセット 2 以降を 57 バイトずつ送り、`e3` で終了する
- `e2` の応答に送信したパケット番号が含まれる
- 更新モードは書き込みが終わるまで、抜き差ししても維持される
- 更新モードで `e1` から再開できる（移行直後からの再開の記述はあるが、転送の途中からの再開は資料でも確定していない）
- 純正 FW と更新モードは USB の表示が同じ

### 参考実装のツールの調査

コミット `0099ac64d30a0530714844fe1fcbaff230fc65fa` の `tools/flash.py` と `tools/hfb_crc.py` を読みました。コードは実行していません。動作の確認は、読んだ内容にもとづくものです。

- 標準ライブラリだけを使い、ネットワークや外部コマンドの呼び出しはない。ファイルへの書き込みは `--trace-log` の追記だけである
- `--list` と `--dry-run` は sysfs と HFB を読むだけで、デバイスを開かない
- 純正 FW への送信は `e0`、`e1`、`e2`、`e3` だけで、応答の先頭と `e2` のパケット番号を確かめ、不一致なら後続を送らない。再送はしない
- ツール自身は次を検査しない。SHA-256、機種の識別子、HFB のサイズ、実機と HFB の版
- `--trace-log` には HFB の内容が 16 進数で残るので、ログは公開しない
- `e1` で通知するサイズはファイル全体の 282,672 バイトで、`e2` で送るのは先頭の 2 バイトを除く 282,670 バイトである

資料の記述のうち、この change の判断に影響するものは次のとおりで、いずれも未検証である。

- 実績として書かれている経路は、純正から QMK、QMK から QMK、QMK から純正、更新モードからの書き込みである。**純正から同じ版の純正への書き込みは、記述がない**。コードに版の判定はない
- 実機と Bluetooth でつながっていると、STM32 の領域と nRF の領域の境目（パケット 1149 の次）で転送が止まることがある。この機種は手元の Mac とペアリング済みである
- 転送の途中で失敗した後の再開は「未確認」とする記述と、Bluetooth を止めて再開できたとする記述が、同じ文書にある。`e3` の応答が異常だった後の動作は未確認である
- nRF への書き込みの仕組みは資料でも未解明である
- キーマップ領域は更新で変わらないと書かれているが、これは資料の作者の逆アセンブルにもとづく。ここでは実機の比較で確かめる

## Goals / Non-Goals

**Goals:**

- 実機に触れる前に、失敗したときの戻り先を確保する
- 未確認の前提を、影響の小さい順に 1 つずつ確かめる

**Non-Goals:**

- 任意の HFB を書き込む汎用ツール。QMK への対応は次の change で要件を定める
- Linux 版の自作ツール。復旧には実績のある参考実装のツールを使う
- 書き込みの中断からの自動復旧、自動の再送

## Decisions

### 確かめる順序を固定する

順序は次のとおりで、前の段階が失敗したら次へ進まない。実機を変更する段階は、それぞれ実行前に承認を得る。

| 順 | 内容 | 実機の変更 |
|---|---|---|
| 1 | Linux 環境から認識できることを送信なしで確認する | なし |
| 2 | 設定をバックアップし、公式ツールでの復元を確認する | キーマップ |
| 3 | Linux から参考実装のツールで純正を再書き込みして、通信を記録する | ファームウェア |
| 4 | 自作ツールをモックで実装し、3 の記録と照合する | なし |
| 5 | macOS から更新モードへ移行する | 更新モード |
| 6 | macOS から本体を書き込む | ファームウェア |

3 を先に行うのは、失敗時の戻り先が実際に使えることを確かめるためと、資料の内容を実機の記録で裏付けて、自作ツールの入力にするためである。自前の観測を優先する方針に合わせ、記録は手元の実機で取る。

- 代替案: macOS の自作ツールを最初に試す。Linux の復旧手順が未確認のまま更新モードに入るので採用しない
- 代替案: 3 を省く。実機への書き込みは 1 回減るが、資料だけを根拠に自作ツールを作ることになり、戻り先も未確認になるので採用しない

### 版を書き換えた HFB は使わない

同じ版の純正 HFB をそのまま書き込む。参考実装の資料では `e1` に版を渡さないので、ブートローダが同じ版を拒否しない可能性がある。3 で確かめる。

### 書き込みはモジュールを分け、許可リストを通す

状態確認とは別の非公開の送信トレイトを持つモジュールにする。公開 API は検査済みの HFB を表す型だけを受け取り、バイト列は受け取らない。この型は SHA-256 の許可リストと CRC、MD5 の検査に通ったときだけ作られる。レポートはこの型から組み立て、CLI の引数からは組み立てない。

- 代替案: HFB のパスを送信処理へ直接渡す。検査を通らない経路が残るので採用しない

### 段階をサブコマンドに分ける

`hhkb flash plan`、`hhkb flash enter`、`hhkb flash write` の 3 つにする。`enter` は `e0` を送って再列挙を確認し、本体を送らずに終了する。`write` は `e1` から始める。

`write` の実行時には純正 FW と更新モードを USB の表示では区別できないので、キー入力できないことを確認文で利用者に確かめる。確認文は段階ごとに固定の文にし、確認を省略するオプションは作らない。

`write` の前に `02` は送らない。更新モードでの応答が未観測だからである。5 の段階で承認を得れば、観測の対象に加えられる。

- 代替案: 1 つのコマンドで最後まで進める。更新モードの見え方を確認してから本体を送るという判断の機会がなくなるので採用しない

### 通信は応答を待って 1 件ずつ進め、再送しない

各レポートの応答を確認してから次を送る。応答のタイムアウトは参考実装に合わせて長めの 60 秒とし、3 の記録で見直す。中止したら再送せず、やり直しは利用者が `write` を実行し直す。

送信形式は状態確認と同じく `hid_write` にレポート ID `0` を先頭に付ける。デバイスは非排他で開く。更新モードで公式ツールとの同時実行を防ぐ確認は `enter`、`write` の両方で行う。

### 再列挙は待ってから選び直す

`e0` の応答の後にデバイスを閉じ、参考実装と同じく 10 秒待ってから、一覧を取り直す。見つからなければ USB の抜き差しを案内して待つ。`0xFF00` が他の用途と分かれていないインターフェースや、USB 以外のものには送らない。

### ログは本体のデータを含めない

`local/` に権限 0600 で JSON Lines を追記する。送信の先頭のバイト、応答の全バイト、時刻を記録する。本体はパケット番号だけを記録し、HFB の内容をログへ複製しない。応答に個体情報が含まれる可能性があるので、ログの内容は公開しない。

### テストはモック HID で行う

送信の順序、パケットの分割、応答の検証、中止時に後続を送らないことをモックで確かめる。テストには合成の HFB を使い、許可リストはテスト用の値を注入する。純正 HFB には依存しない。

## Risks / Trade-offs

- [macOS から更新モードのインターフェースを開けない] → `enter` で止まるので本体は送っていない。Linux 環境から純正を書き込んで戻す
- [Bluetooth の接続で転送が止まる] → 書き込みの前に、周囲の Mac と Linux の Bluetooth を切り、キーボードが接続できない状態にする。止まったら USB を抜き差しして、Bluetooth が切れていることを確認してから再開する
- [本体の書き込みが途中で止まる] → 資料では更新モードのまま待機するとされるが、途中からの再開は実績が限られる。`write` でやり直し、だめなら Linux から書き込む。Linux でも認識しない場合の最終手段は分解で、その判断はユーザーに委ねる
- [nRF の領域の書き込みで問題が起きる] → 仕組みが未解明なので、確認できない。Bluetooth を切り、完了後に Bluetooth の入力を確認する。問題が起きたら進まずにユーザーと判断する
- [参考実装のツールは HFB の内容をほとんど検査しない] → 実行前に SHA-256 を手で照合し、`--allow-crc-mismatch` は使わない
- [Linux でも更新モードに入らない、戻らない] → 3 が失敗した時点で macOS の段階に進まない。原因を記録してユーザーと判断する
- [再書き込みで設定が失われる] → 2 のバックアップを公式ツールで復元し、読み出しの記録と全バイトを比較する
- [純正 FW で `write` を実行する] → 確認文でキー入力できないことを確かめる。起きたときの動作は未確認なので、誤りに気づいたら実行しない
- [Mac のスリープ、USB の抜け] → `caffeinate` を併用して実行する手順にする。電源とケーブルを実行前に確認する。ハブを使わず直結する
- [ブートローダが同じ版を拒否する] → 3 で分かる。この場合は macOS の段階に進まず、進め方をユーザーと決める
- [保証への影響] → 実行前に承認を得る段階で改めて提示する。法的な判断はしない
- [参考実装のツールに問題がある] → コミットを固定し、実行前に全文を読む。リポジトリには含めない

## Migration Plan

設定はバックアップから公式ツールで戻す。書き込みの CLI を使わなければ、既存の動作は変わらない。この change の途中で中断するときは、実機を純正で動作する状態に戻してから止める。
