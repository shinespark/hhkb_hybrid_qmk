# Design

## Context

目的は proposal.md を参照。`hhkb flash` は純正 FW の動作中と更新モードだけを想定している。`select_target` は `0xFF00` で台数を数えるので、QMK の動作中は「インターフェースがない」と判定する。`hhkb status` は `0xFF00` へ `02` を送る。

手元で観測済みの内容:

- 純正 FW と更新モードでの `e0`〜`e3`。macOS と Linux の両方で純正を書き込めた
- 生成した HFB の検査と、参考実装のツールとの一致

次の内容は参考実装の資料とコードだけが根拠で、この change の観測で確かめる。

- QMK の動作中は製品名が `HHKB Hybrid QMK` で、`0xFF60` のインターフェースに 32 バイトで送受信する
- QMK への `aa aa e0 00 00` の応答が `55 55 e0 00 00` で、更新モードへ移行する
- `aa aa f0 00 00` は `via` では VIA の保存領域を消して移行し、`default` では `55 55 f0 01 00` で拒否する
- VIA の問い合わせ（先頭 `01`）に、`via` だけが先頭 `01` で応答する
- `default` は純正のキーマップ領域を使わず、`via` の領域は `f0` で消える
- Esc を押しながら USB を接続すると更新モードへ入る
- QMK で Bluetooth に登録した接続先が純正 FW に引き継がれ、青 LED が点灯したまま入力できないときは Fn + Ctrl + 0 で USB に切り替える

## Goals / Non-Goals

**Goals:**

- 純正と QMK の間を macOS だけで行き来できることを、実機で確かめる
- 戻す手順を確かめてから、実用の `via` へ進む

**Non-Goals:**

- 許可リストにない HFB の書き込み、任意のレポートの送信
- キーマップの変更。`via` の変更は VIA の画面で行う

## Decisions

### 確かめる順序を固定する

順序は次のとおりで、前の段階が失敗したら次へ進まない。各段階の `enter` と `write` は、それぞれ実行前に承認を得る。

| 順 | 書き込み | 確かめること |
|---|---|---|
| 1 | 純正 → `default` | 受理、起動、キー入力、更新モードへ戻れる見込み |
| 2 | `default` → 純正 | macOS だけで戻れること、設定が基準と一致すること |
| 3 | 純正 → `via` | 起動、VIA での変更と保持 |
| 4 | `via` → 純正 | `f0` で VIA の設定が消え、設定が基準と一致すること |
| 5 | 必要なら 純正 → `via` | ユーザーが決めた最後の状態 |

- 代替案: 最初に `via` を書く。`via` は戻すときに消す領域が増えるので、最初の確認には向かない。採用しない
- 代替案: 4 を省く。書き込みは減るが、`via` から戻せることが未確認のまま実用に入るので採用しない

### 状態は製品名とインターフェースの両方で判定する

| 状態 | 製品名に `QMK` | インターフェース | 扱い |
|---|---|---|---|
| 純正 FW または更新モード | なし | `0xFF00` | 今までどおり |
| QMK の動作中の可能性が高い | あり | `0xFF60` | QMK の手順 |
| 確定できない | 上の組み合わせ以外 | | 書き込みの段階へ進まない |

`0xFF60` のインターフェースが他の用途と分かれていないときは開かない。USB 以外のものは今までどおり除く。実機の表示が資料と異なれば、ここで止まるので送信は起きない。

### レポートの長さを型で分ける

送信のトレイトを 64 バイト固定から、`Frame` と長さを分ける形に変える。QMK へのフレームは `e0`、`f0`、VIA の問い合わせの 3 種類だけを固定で組み立てる。本体の転送は今までどおり 64 バイトだけで、更新モードにしか送らない。

### 移行のコマンドと VIA の確認

`f0` の応答が受理（4 バイト目 `00`）なら移行として扱う。拒否（`01`）なら VIA の問い合わせを 1 回送り、1 秒以内に先頭 `01` の応答があれば中止する。応答がなければ `e0` を送る。参考実装のツールと同じ判断である。

VIA の問い合わせは、参考実装のコードを読んで固定値を確かめた。承認の範囲を明確にするため、QMK への送信は上の 3 種類に限り、引数から組み立てない。

### 許可リストに種類を持たせる

許可リストを SHA-256 と種類の組にする。種類は純正、QMK の `default`、QMK の `via` である。テストは今までどおり値を注入する。`hfb.rs` の機種と版の検査はそのまま通す。

追加する値は `default` が `abc86297c4f0d4d967fe9e1bfa8b5491b4a99873afb58e57d93d2f3ebf1cdcf4`、`via` が `1393125de1bd6b24c64b424b1398e1fe1aa1e104f26609fc045130a2042e223e` である。

### 確認文に種類を含める

確認文は段階と種類の組ごとに固定する。別の段階や別の種類の文では進まない。QMK を書き込むときは、保証への影響と、戻せない場合に分解が必要になる可能性を同じ画面に表示する。

### 更新モードの再選択は今までどおり

移行の後は、QMK から移行した場合も `0xFF00` だけを選び直す。`0xFF60` が見えている間は更新モードではないと扱い、送らずに待つ。QMK は応答の後で USB を切断するので、応答の後の受信のエラーは待機の扱いにせず、応答を受けた時点で移行の成功とする。

### 実機の確認で公式ツールの扱いを分ける

純正 FW の動作中だけ、公式ツールの `read` を実行する。QMK の動作中に公式ツールを起動しない。送信の内容が未確認で、純正を前提とする書き込みが起きる可能性があるためである。

## Risks / Trade-offs

- [QMK が起動しない、入力できない] → 資料によれば起動判定は CRC だけで、壊れたアプリでも起動扱いになる。参考実装の実績があるのは同じ定義の `.bin` で、まず Esc を押しながらの接続で更新モードを試し、Linux の `--resume` で純正を書く。だめなら分解で、判断はユーザーに委ねる
- [QMK から更新モードへ戻れない] → 同上。最初に `default` を使い、次の段階へ進む前に戻せることを確かめる
- [固定したコミットの動作が未検証] → 公開値と一致するのは古い定義だけである。最初の起動で確かめる項目に含める
- [途中で止まった状態から戻せない] → ユーザーの判断で試さない。書き込みの承認のたびに提示する
- [Bluetooth の接続先が変わる] → 純正へ戻した後に入力できなければ Fn + Ctrl + 0 を試す。接続先の再登録が要る可能性を提示する
- [設定が変わる] → 純正へ戻した後に基準の `read` と比較し、変わっていれば `.hks` で戻す。mode `11` が変わった場合の復元は未確認である
- [製品名の判定が外れる] → 確定できない状態として止まる
- [VIA の Web アプリ] → 外部のサイトに USB の接続を許可する。使うのはユーザーで、書き込みの間はタブを閉じる
- [保証への影響] → 実行前の承認で提示する。法的な判断はしない

## Migration Plan

実機は純正へ戻せる。コードは既存の純正の経路を変えない。途中で中断するときは、実機を純正か、動作を確認した QMK のどちらかで止める。

- 最後に残す状態。実機の結果を見てユーザーが決める。タスクの 6.1 で確定する
