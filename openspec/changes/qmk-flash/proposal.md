# Proposal

## Why

QMK の HFB は生成できたが、実機が受理して起動するかは未確認で、macOS から QMK を書き込む手段も、QMK から macOS だけで純正へ戻す手段もない。今の `hhkb flash` は純正 FW の動作中だけを想定していて、資料によれば、QMK の動作中はインターフェース、レポート長、純正へ戻すときのコマンドが異なる。実用する前に、戻れることを含めて macOS で確かめる。

## What Changes

- `hhkb flash` の許可リストに、`qmk-build-hfb` で生成した `default` と `via` の HFB を追加する
- USB の製品名とインターフェースから QMK の動作中を見分け、QMK の Raw HID（`0xFF60`、32 バイト）で更新モードへ移行できるようにする
- HFB の種類に応じて移行のコマンドを選ぶ。QMK の動作中に純正へ戻すときは、VIA の設定を消す `F0` を先に送る
- QMK の動作中に、本体の書き込みを始めないようにする
- `hhkb list` と `hhkb status` が QMK の動作中も使えるようにする。QMK には `02` を送らない
- 承認を得て、次の順に実機で確かめる
  1. 純正から `default` へ書き込み、動作を確認する
  2. `default` から純正へ戻し、設定が基準と一致することを確認する
  3. 純正から `via` へ書き込み、VIA での変更と保持を確認する
  4. `via` から純正へ戻し、設定が基準と一致することを確認する
  5. 最後に残す状態をユーザーが決める
- 結果を `docs/analysis/findings.md` と `README.md` に記録する
- 範囲外:
  - キーボード定義の自作、キーマップの変更
  - 途中で止まった状態から戻せるかをわざと止めて確かめること
  - 分解による DFU の実施
  - 許可リストにない HFB の書き込み

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `firmware-update`: 対象を生成した QMK の HFB に広げ、QMK の動作中の移行と、純正へ戻すときの手順を追加する
- `device-status`: QMK の動作中も 1 台として認識し、純正と区別して表示する。QMK には固定レポートを送らない
- `hfb-generation`: 生成した HFB を書き込みの対象から除く要件を取り除く

## Impact

- コード: `crates/hhkb` の `flash`、`device`、`status`、CLI
- 実機: ファームウェアを最大 4〜5 回書き込む。設定が変わる可能性がある。Bluetooth の接続先の情報が変わる可能性がある
- **リスク**: QMK が起動しても更新モードへ戻れないと、Esc を押しながら接続する操作か、最悪の場合は分解が必要になる。途中で止まった状態からの復旧は未検証である。保証に影響する可能性がある
- 外部: 失敗に備えて Linux 環境を起動しておく。VIA の確認に Chrome か Edge と外部の Web アプリを使う
- 法的な扱い: 生成した HFB と `.bin` は引き続き公開も配布もしない。適法性は判断せず、利用の判断はユーザーに委ねる
