# Design

## Context

目的は proposal.md を参照。`crates/hhkb` には HFB の検査と、許可リストで守った `hhkb flash` がある。領域 A の CRC と全体の CRC の計算は、純正 HFB の観測で確かめた `hfb::crc16` がある。

参考実装のコミット `0099ac64d30a0530714844fe1fcbaff230fc65fa` について確かめた内容（読むだけで、実行していない）:

- QMK 本体を submodule でコミット `08c662f286ddfd12a985f57b584b02eca5af0ae6` に固定している
- QMK 公式のイメージをダイジェスト `sha256:b7d7fa8fb4432b569931de5ad59098cb788f440ed61a62c5126746b71aee0f4a` に固定している。このダイジェストは `linux/amd64` と `linux/arm64` に対応する
- `.bin` の SHA-256 の公開値は、`default` が `70a90ee725d76077692a4d1c32cc07839860590dc4c12f1a799b712ead700dc6`、`via` が `b5d82c52c1f8ed37856cc7c623d539d79ae1eba3a5e8c369f8dd301058a98aa5`。手元で再現できるかは未確認で、どの CPU でビルドした値かも記述がない
- `tools/build.sh` は定義を QMK 本体へコピーしてビルドする
- `tools/qmk_to_hfb.py` は純正 HFB の領域 A を `.bin` で置き換えて、余りを `0xFF` で埋め、2 つの CRC を計算し直す

手元の Mac には Docker、qmk、ARM のツールチェインがない。CPU は arm64 である。

## Goals / Non-Goals

**Goals:**

- 参考実装と同じ入力から、同じ `.bin` を手元で再現する
- HFB の生成を Rust で実装し、参考実装のツールと同じ結果になることを確かめる

**Non-Goals:**

- 任意の `.bin` や keymap からの生成。キーマップを変える段階で、許可の考え方を決め直す
- 生成した HFB の書き込み。次の change で要件を定める

## Decisions

### 参考実装は submodule で参照し、定義をコピーしない

`third_party/hhkb_hybrid` に固定する。QMK 本体は参考実装が固定したコミットをたどって取得し、ビルドに要る `lib/` の submodule だけを取得する。

- 代替案: ファイルをコピーする。自由に編集できるが、逆アセンブル由来の知見を公開リポジトリに含めることになるので採用しない
- 代替案: 定義を自作する。ユーザーの判断で今回は見送った。必要な事実が資料頼みのうえ、更新モードへ戻れないと分解が要るリスクがある

### ビルドの実行は Rust から Docker を固定の引数で呼ぶ

`hhkb qmk build <default|via>` が、入力の確認、Docker の実行、SHA-256 の照合を行う。参考実装の `tools/build.sh` は実行しない。外部のシェルスクリプトを手元で実行せずに済み、照合と出力先を自分で管理できる。

キーボード定義は読み取り専用でコンテナにマウントし、成果物の `.build` は `local/qmk-build/` にマウントする。参考実装のコピーと違い、QMK 本体の作業ツリーを変更しない。コンテナ内のパスは参考実装の手順と同じにする。

- 代替案: `tools/build.sh` をそのまま実行する。手順は完全に同じになるが、上の理由で採用しない。下記の照合で差が出たら、差の原因の切り分けに使うかをユーザーと判断する

### `.bin` の照合が通らなければ先へ進まない

最初に `linux/arm64` のイメージでビルドして照合する。一致しなければ、エミュレーションの `linux/amd64` でビルドして比べる。それでも一致しないときは、参考実装の手順との差を調べ、進め方をユーザーと決める。不一致のまま期待する値を書き換えない。

### HFB の生成は検査済みの型から作る

`hhkb qmk hfb <default|via> --stock <純正 HFB> --out <出力先>` とする。テンプレートは `VerifiedHfb` だけを受け取り、`.bin` は keymap ごとの許可リストで確かめる。生成物は `hfb::inspect` の検査に通ってから、権限 0600 で新規作成する。

`VerifiedHfb` にテンプレートの本体を渡す内部の口を足すが、公開 API から任意のバイト列を送信する経路は作らない。生成した HFB は `hhkb flash` の許可リストに入らないので、書き込みの経路とは分かれたままになる。

- 代替案: 参考実装の `qmk_to_hfb.py` を使う。Rust で実装する方針と、自前の検査を通す目的から採用しない。結果の照合にだけ使う

### 生成結果を参考実装のツールと照合する

Linux 環境の固定コミットで `qmk_to_hfb.py` を実行し、Rust の生成物と SHA-256 を比べる。既存の環境を使うので Mac に Python の実行を増やさない。ツールはファイルの読み書きだけで、実機に送信しない。`.bin` は SSH で Linux に渡す。

## Risks / Trade-offs

- [`.bin` を再現できない] → 上の手順で切り分ける。解決しなければ次の段階に進まない
- [読み取り専用のマウントで結果が変わる] → SHA-256 の照合で分かる。差が出たら参考実装と同じコピーの方法に変える
- [submodule の参照先が消える、履歴が書き換えられる] → コミットの確認で失敗し、誤った内容ではビルドしない。Linux 環境に同じコミットの複製がある
- [参照先の内容を信頼する] → ビルドはコンテナの中で行い、Mac へは `local/` と QMK 本体の作業ツリーだけをマウントする。生成物を実機に書く判断は次の change で行う
- [成果物の誤った公開] → `local/` と `*.hfb` は Git の管理外である。`.bin` も `local/` に置く
- [Docker Desktop の利用条件] → 導入の前にユーザーが確認する
- [ディスク容量とネットワーク] → QMK 本体と `lib/` は必要な分だけ取得する

## Migration Plan

既存の動作は変わらない。やめるときは submodule と `qmk` サブコマンドを取り除き、Docker Desktop を削除する。

## Open Questions
